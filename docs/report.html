1. Problem Statement & Assignment Objectives

At ReachInbox.ai, reliable scheduling and automated dispatch of cold email outreach sequences at scale is a mission-critical infrastructure requirement. Simple in-memory timers (setTimeout) or cron jobs fail in real production because:

  • Server Crashes / Restarts: In-memory queues lose all scheduled tasks immediately on process restart.
  • Cron Inefficiency: Cron jobs poll databases on fixed intervals, creating race conditions, duplicate dispatches, and CPU waste.
  • Rate Limiting & Burst Protection: Without queue-level throttling, sending bulk emails triggers SMTP provider rate limits.

Core Assignment Goal: Build a fault-tolerant email scheduler service and modern SaaS dashboard that accepts email scheduling requests via REST API & UI, persists them using BullMQ + Redis delayed sorted sets (surviving abrupt restarts), sends via Ethereal Fake SMTP with live rendered web preview links, and provides full lifecycle controls (Reschedule, Cancel, Throttling).

3. How Server Restart Resilience Works (BullMQ + Redis)

Key Architectural Advantage: Unlike memory queues, BullMQ writes delayed tasks directly to Redis as sorted sets where the score is the target Unix execution timestamp (now + delayMs).
  1. Job Enqueueing: When an email is scheduled, BullMQ computes delay = scheduledAt - now and persists the job payload in Redis under key bull:email-scheduler-queue:delayed.
  2. Crash & Restart: If the Express server or Worker process terminates abruptly, Redis persistence (AOF / RDB) retains the delayed sorted set unharmed.
  3. Worker Discovery: When the backend server restarts, the BullMQ Worker automatically reconnects to Redis, re-evaluates the delayed sorted set, and executes the pending jobs at the exact target time.
  4. Zero Duplicates: Distributed locks (atomic Lua scripts) ensure that only a single worker acquires and processes each email job once.

6. Technical Interview & Viva Guide

Q1: Why BullMQ + Redis over Cron Jobs (node-cron)?
Answer: Cron jobs are interval-based pollers that query the DB repeatedly, wasting CPU cycles and causing synchronization bottlenecks across multi-instance clusters. BullMQ uses Redis sorted sets to hold delayed jobs and activates workers via event-driven pub/sub and atomic Lua scripts precisely when the Unix timestamp elapses, with built-in concurrency control and crash recovery.
Q2: How does the system guarantee no double-sends on server crashes?
Answer: BullMQ uses atomic lock leases (lockDuration: 30000ms). When a worker begins processing, it claims exclusive lock ownership. If the server crashes during execution, the lock expires after the stalled interval (stalledInterval: 15000ms), and a restarted worker resumes the job cleanly without duplicate executions.
Q3: How is rate limiting and throttling enforced?
Answer: The scheduler computes staggered delay offsets for batch leads: itemDelayMs = baseDelayMs + (index * minDelaySeconds * 1000). Additionally, the backend tracks hourly quota dispatches and blocks incoming schedules that exceed the 200 emails/hour threshold.
Q4: How do you verify emails without hitting spam filters or real users?
Answer: We integrated Nodemailer with Ethereal SMTP test accounts. Ethereal simulates full RFC-compliant SMTP handshakes, accepts emails, and generates a live rendered web viewer URL (nodemailer.getTestMessageUrl(info)) displayed directly in the dashboard UI.
