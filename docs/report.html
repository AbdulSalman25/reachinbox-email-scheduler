3. 🛡 System Architecture & Crash Resilience Mechanism

Why BullMQ + Redis instead of Cron Jobs?
Cron jobs (node-cron) poll databases on fixed tick intervals. Under high scale, this causes CPU thrashing, duplicate dispatches across multiple backend instances, and lost tasks if the server is down during the cron tick. BullMQ uses Redis sorted sets (zset) where delayed jobs are indexed by target Unix epoch timestamp.

How Server Restarts and Crashes are Handled:

  1. Delayed Job Enqueueing: When POST /api/emails/schedule is called, BullMQ computes delay = scheduledAt - now and writes the job payload to Redis sorted set bull:email-scheduler-queue:delayed.
  2. Crash Survival: If the server or worker crashes, Redis persistence (AOF / RDB) retains the job unharmed.
  3. Automatic Worker Recovery: Upon rebooting, the BullMQ Worker re-attaches to the queue, discovers the pending delayed tasks, and fires them precisely when the timestamp is reached.
  4. Atomic Distributed Locks: BullMQ acquires atomic Lua lock leases (lockDuration: 30000ms), guaranteeing that only one worker instance executes each email job with zero duplicates.

4. ⚡ Rate Limiting & Throttling Engine

To comply with SMTP provider limits and prevent spam flags, two throttling layers are enforced:

  • Min Delay per Send (s): When multiple recipient leads are scheduled in a batch, the engine applies staggered delays: 
    itemDelayMs = baseDelayMs + (index * minDelayPerSend * 1000);
  • Hourly Quota (200 emails/hr): Tracks dispatches in the current 60-minute window and displays a real-time progress bar on the dashboard (0 / 200 sends left).

6. 💻 Core Code Highlights

1. BullMQ Delayed Queue Enqueueing (queue.service.ts)

export const addDelayedEmailJob = async (jobData: EmailJobPayload, delayMs: number) => {
  return await emailQueue.add('send-scheduled-email', jobData, {
    jobId: jobData.emailId,
    delay: Math.max(0, delayMs),
    attempts: 3,
    backoff: { type: 'exponential', delay: 5000 },
    removeOnComplete: false,
    removeOnFail: false,
  });
};

2. Background Worker Processing & Ethereal Link Generation (email.worker.ts)

export const initEmailWorker = () => {
  const worker = new Worker('email-scheduler-queue', async (job: Job<EmailJobPayload>) => {
    const { emailId, to, subject, body, senderProfile } = job.data;
    await prisma.emailJob.update({ where: { id: emailId }, data: { status: 'PROCESSING' } });

    const info = await sendMail({ from: senderProfile, to, subject, text: body });
    const previewUrl = nodemailer.getTestMessageUrl(info) || null;

    await prisma.emailJob.update({
      where: { id: emailId },
      data: { status: 'SENT', sentAt: new Date(), etherealPreviewUrl: previewUrl, etherealMessageId: info.messageId }
    });
  }, { connection: getRedisConnection(), concurrency: 5 });
  return worker;
};

7. 🎯 Technical Interview Q&A Reference

Q1: Why BullMQ + Redis over Cron Jobs (node-cron)?
Answer: Cron jobs are interval-based pollers that query the DB repeatedly, wasting CPU cycles and causing synchronization bottlenecks across multi-instance clusters. BullMQ uses Redis sorted sets to hold delayed jobs and activates workers via event-driven pub/sub and atomic Lua scripts precisely when the Unix timestamp elapses, with built-in concurrency control and crash recovery.
Q2: How does the system guarantee no double-sends on server crashes?
Answer: BullMQ uses atomic lock leases (lockDuration: 30000ms). When a worker begins processing, it claims exclusive lock ownership. If the server crashes during execution, the lock expires after the stalled interval (stalledInterval: 15000ms), and a restarted worker resumes the job cleanly without duplicate executions.
Q3: How is rate limiting and throttling enforced?
Answer: The scheduler computes staggered delay offsets for batch leads: itemDelayMs = baseDelayMs + (index * minDelaySeconds * 1000). Additionally, the backend tracks hourly quota dispatches and blocks incoming schedules that exceed the 200 emails/hour threshold.
